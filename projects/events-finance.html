Why re-finding invoices by filename had to go.

The problem

Every event has quotes, approvals, invoices and payments, often from several vendors at once. Each step needs the right person's sign-off, and every invoice has to stay attached to the right event all the way to payment.

What I built

  • Scale: six flows built, with a seventh planned.
  • Data model: one list item per invoice, with several allowed per event. A file-naming convention links them.
  • Approvals: tiers routed by amount and event type, using Teams and Outlook approval cards.
  • Reporting: Power BI.
  • Supporting material: a "hard-won fixes" table and a system diagram.

How it works

The diagram is a sanitized redraw: it leaves out site names, paths, mailboxes, approval thresholds and internal expressions.

Key decisions

Root-cause debugging: resolve once, where it's reliable

Every flow used to re-find invoices by filename pattern. That failed silently when a name was slightly off, and it picked the wrong vendor's file when an event had several. The fix was a capture flow that stores the invoice's file ID once, so later flows reference it directly.

The principle I took from it: "resolve once, where it is reliable."

Results and status

As of Sept 23, 2026, the four main flows and one payment authorization passed end-to-end testing, and the capture flow was next to build.

What I'd do next

  • Build the capture flow, so every later step uses the stored file ID.
  • Finish the seventh flow.
